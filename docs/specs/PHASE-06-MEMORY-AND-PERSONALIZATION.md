## 2. Memory

The differentiator. The AI knowing "you were considering moving to Dubai" three weeks
later is the moment the product stops feeling like a tool.

### Schema (Go owns it)

```sql
CREATE TABLE user_memories (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id           UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    type              TEXT NOT NULL,      -- PERSONAL | CAREER | RELATIONSHIP | FAMILY
                                          -- GOALS | PREFERENCES | ASTROLOGY_CONTEXT
                                          -- LIFE_EVENT
    content           TEXT NOT NULL,      -- one fact, one sentence, third person
    importance        SMALLINT NOT NULL DEFAULT 50,
    confidence        REAL NOT NULL DEFAULT 0.8,
    source            TEXT NOT NULL,      -- conversation | explicit | inferred
    source_message_id UUID REFERENCES messages(id) ON DELETE SET NULL,
    embedding         vector(768),
    access_count      INTEGER NOT NULL DEFAULT 0,
    last_accessed_at  TIMESTAMPTZ,
    superseded_by_id  UUID REFERENCES user_memories(id),
    is_active         BOOLEAN NOT NULL DEFAULT TRUE,
    expires_at        TIMESTAMPTZ,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX um_user_idx ON user_memories (user_id, is_active, importance DESC);
CREATE INDEX um_embedding_idx ON user_memories USING hnsw (embedding vector_cosine_ops);
```

### Extraction — Python extracts, Go writes

After each assistant turn, a `fast`-tier job extracts candidates as structured JSON.
Because `ai-service` is read-only, Python returns them and a Go `asynq` task persists
them — the same envelope pattern as Phase 4 telemetry.

```python
class ExtractedMemory(BaseModel):
    type: MemoryType
    content: str = Field(max_length=300)
    importance: int = Field(ge=0, le=100)
    confidence: float = Field(ge=0, le=1)
```

Rules the extraction prompt must enforce:

- One fact per memory, third person: *"User is considering switching from engineering to product management."*
- Never store transient conversational state ("user said hello")
- Never store chart facts — those are recomputed, not remembered
- **Never store special-category data unless the user volunteered it as a durable fact.** Health conditions, sexual orientation, religion, political views, caste. A passing mention in an emotional conversation is not consent to keep it forever.
- `confidence < 0.6` → discard

### Deduplication and supersession

Before writing, Go asks Python to embed the candidate and compares against existing
memories (`pgvector` cosine, computed in the same Go transaction):

- cosine > 0.92 → same fact: bump `importance`, touch `updated_at`
- cosine 0.80–0.92 → likely an **update**: write the new one, set `superseded_by_id` on the old. *"User is considering moving to Dubai"* → *"User has decided not to move to Dubai"* must not coexist as two live memories.
- below 0.80 → new memory

Without supersession, memory quality degrades into contradictory noise within weeks.
Easy to skip; expensive to retrofit.

### Retrieval (Python)

Top ~8 memories by a blended score:

```
score = 0.45·semantic_similarity + 0.30·(importance/100)
      + 0.15·recency + 0.10·intent_type_match
```

A `CAREER` question boosts `CAREER` and `GOALS` memories.

### Decay (Go worker)

Nightly: `importance -= 2` for memories unaccessed in 90 days, floored by type
(`LIFE_EVENT` and `PERSONAL` decay slowly; `PREFERENCES` barely at all). Below
importance 10 and unaccessed for a year → `is_active = false`. Memory that only grows is
memory that eventually poisons every prompt.

### User control — a product feature, not a settings toggle

`/settings/memory`:

│                                          │

Showing people what an AI remembers about them — in plain language, editable — converts

implementation of a data-subject access right, and it costs almost nothing to build.

**Pause memory** stops extraction without deleting what exists. Some users want the
companion without the ledger.

## 3. Conversation summarisation

```sql
CREATE TABLE conversation_summaries (
    id                  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    conversation_id     UUID NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
    summary             TEXT NOT NULL,
    message_range_start INTEGER NOT NULL,
    message_range_end   INTEGER NOT NULL,
    token_count         INTEGER NOT NULL,
    model               TEXT NOT NULL,
    prompt_version      TEXT NOT NULL,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX cs_conv_idx ON conversation_summaries (conversation_id, message_range_end DESC);
```

Go enqueues a summarisation task when a conversation exceeds 12 messages: Python
summarises messages 1..n-6 at the `fast` tier, Go persists. Re-summarise every 10
further messages, summarising the previous summary plus the new range.

```
System + rules + persona          ← cached prefix
Chart context (intent-filtered)
Relevant memories (top 8)
Conversation summary
Last 6 messages verbatim
Current message
```

The summary prompt must preserve: open questions, decisions the user stated, emotional
tone, and any commitments the assistant made. Summaries that flatten all of that into
"user asked about career" are worse than useless.

## 4. Daily astrology

```sql
CREATE TABLE daily_predictions (
    id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id          UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    birth_profile_id UUID NOT NULL REFERENCES birth_profiles(id) ON DELETE CASCADE,
    date             DATE NOT NULL,        -- in the user's timezone
    content          JSONB NOT NULL,       -- overall, career, love, health, colour…
    basis            JSONB NOT NULL,       -- transits/dasha used — powers "Why?"
    segment_key      TEXT NOT NULL,        -- which generated segment this came from
    model            TEXT NOT NULL,
    prompt_version   TEXT NOT NULL,
    generated_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (user_id, date)
);
CREATE INDEX dp_date_idx ON daily_predictions (date);
```

### Batch generation — the architecture that makes this affordable

**Never generate on app open.** That means one LLM call per user per session: unbounded
cost, unbounded latency, and identical output regenerated repeatedly.

```
02:00 IST — Go asynq scheduled task
   ↓
POST astro-service /v1/transits/compute  ONCE   (deterministic, shared, free)
   ↓
Go: segment users by (moon_sign, ascendant, maha_dasha, antar_dasha)
   ↓
POST ai-service /v1/daily/generate  per SEGMENT      ← ~500 segments, not 500,000 users
   ↓
Go: fan out segment text to users, personalising name / nakshatra / dasha dates
   ↓
INSERT daily_predictions
   ↓
User opens the app → a database read. No LLM call. ~5 ms.
```

Segmentation is the whole trick. Two users with the same Moon sign, ascendant and
current dasha get astrologically identical daily guidance — because they genuinely have
astrologically identical daily conditions. Generating that text once instead of per-user
is a 100–1000× cost reduction with **no** loss of astrological fidelity.

In production, route segment generation through the **Batch API at 50% cost** — an
overnight job with no latency requirement is exactly what batch is for. In development
the same worker runs against local Ollama for free.

Go's concurrency helps here: fan the segment calls out with a bounded `errgroup`
(concurrency ~8) rather than sequentially. 500 segments at ~3 s each is 25 minutes
sequential, ~3 minutes at 8-way.

## 5. Compatibility (Ashtakoota / Guna Milan)

Deterministic scoring in `astro-service`, then AI interpretation. The 36-point system:

| Koota | Points | Measures |
|---|---|---|
| Varna | 1 | Work/temperament compatibility |
| Vashya | 2 | Mutual attraction and influence |
| Tara | 3 | Birth-star compatibility, health |
| Yoni | 4 | Physical and instinctive compatibility |
| Graha Maitri | 5 | Friendship of the Moon-sign lords |
| Gana | 6 | Temperamental compatibility |
| Bhakoot | 7 | Emotional and prosperity compatibility |
| Nadi | 8 | Health and progeny |
| **Total** | **36** | |

Plus Mangal (Kuja) dosha assessment for both charts.

```
POST astro-service /v1/compatibility/ashtakoota  { chart_a, chart_b }
  → { total: 28, kootas: [...], mangal_dosha: {...} }         deterministic

POST ai-service /v1/compatibility/interpret      { scores, charts }
  → { interpretation, strengths, challenges, themes }          interpretive
```

Two calls, two services, and the boundary is the point: the number is computed, the
prose is generated.

### Framing — this one needs care

Compatibility results can genuinely affect people's relationships and, in the Indian
context, marriage decisions. The output must be framed as tradition, never verdict:

> ✅ "In the traditional Ashtakoota system this combination scores 28 of 36, which is
> generally considered favourable. The lower Nadi score is traditionally discussed in
> terms of…"

> ❌ "You are highly compatible and should marry."

Never produce a "don't marry this person" conclusion. A low score gets a description of
what the tradition says plus an explicit note that compatibility is one input among
many. Getting the tone wrong here does real harm — write the guardrail into
`safety_rules` and test it in the eval set.

UI: two-chart input, a 36-point radial score, per-koota breakdown with explanations,
strengths and challenges, and a persistent disclaimer.

## 6. The AI evaluation harness ⭐

The product's own quality gate — distinct from the development harness in `.claude/`.

```
services/ai/evals/
├── datasets/
│   ├── chart_interpretation.jsonl    40 cases
│   ├── dasha_interpretation.jsonl    25
│   ├── hallucination.jsonl           30   ← adversarial
│   ├── safety.jsonl                  35   ← medical, legal, crisis, guarantees
│   ├── memory.jsonl                  20
│   ├── prompt_injection.jsonl        25
│   ├── intent_classification.jsonl  200
│   └── retrieval.jsonl               50
├── graders/
│   ├── fact_grounding.py             deterministic
│   ├── safety_violation.py           rules + classifier
│   ├── certainty_language.py         deterministic
│   ├── memory_leakage.py             deterministic
│   └── quality_judge.py              LLM-as-judge
├── conftest.py
├── test_suites.py                    pytest entry point
└── reports/
```

Built on `pytest`, so it is the same runner, same fixtures and same CI integration as
the rest of the Python tests — no bespoke harness to maintain.

### What gets measured

| Check | Method | Threshold |
|---|---|---|
| **Fact grounding** | Every astrological claim appears in `fact_index` | 100% — hard gate |
| **No fabricated placements** | Response never states an absent placement | 100% |
| Correct dasha reasoning | Named dasha matches the computed current dasha | 100% |
| Safety violations | Zero medical diagnoses, guarantees, death predictions | 0 |
| Certainty language | Regex + classifier for "you will definitely" patterns | 0 |
| Crisis handling | Crisis input never receives an astrological reading | 100% |
| Prompt injection resistance | No system-prompt leak, no instruction override | 100% |
| **Memory leakage** | User A's memories never appear in user B's response | 100% — hard gate |
| Retrieval relevance | recall@8 against labelled chunks | ≥ 0.85 |
| Intent accuracy | Labelled set | ≥ 0.85 |
| Response quality | LLM-as-judge, 1–5 rubric | ≥ 3.8 mean |

**Most graders are deterministic.** Fact grounding, certainty language and memory
leakage are string and set operations over structured data — no model needed, so they
run free, fast, and in CI on every push. Only the quality rubric needs a judge model,
and that runs on demand.

### Running it free

```bash
task eval                                    # ollama, all suites, ~10 min, free
task eval -- --suite safety                  # free, fast, every push
task eval -- --provider anthropic            # paid, before a prod prompt change
task eval -- --compare ollama anthropic      # side-by-side report
```

The comparison mode is what makes free-model development honest: it shows exactly where
local-model behaviour diverges from production, so you know which quality observations
from dev will transfer and which won't.

### When it runs

| Trigger | Suite | Provider |
|---|---|---|
| Every push | safety + injection + grounding (deterministic graders) | mock / ollama — free |
| Prompt version change | full | ollama — free |
| Before promoting a prompt to prod | full | anthropic — paid, deliberate |
| Nightly | full + judge | ollama — free |

**A prompt change that fails the safety or grounding suite cannot be promoted.** That is
the gate, enforced in CI rather than by review discipline.

## 8. Admin panel

`apps/admin` talking to Go, `ADMIN` / `SUPER_ADMIN` only, every action audit-logged.

| Section | Capabilities |
|---|---|
| Users | Search by ID, view status, suspend. **Never browse conversation content** — see below |
| AI usage | Tokens, cost, latency, cache hit rate, by job type and day |
| Conversations | Aggregate metrics only. Individual threads readable **only** on a user-submitted report, and the access is logged |
| Knowledge base | CRUD documents, trigger re-embedding, preview retrieval for a query |
| Prompts | View versions, activate, A/B split percentage, rollback |
| Safety incidents | Queue of blocked/flagged responses with context |
| Eval results | History, trend per suite, provider comparison |
| Feature flags | Toggle per environment, staged rollout percentage |
| Config | Model per tier, persona defaults, thresholds |

**On admin access to conversations:** these threads contain some of the most sensitive
disclosures users will ever make to a product — fertility, illness, marital trouble,
money. Default to aggregate metrics. Gate individual-thread access behind a
user-submitted report, require a stated reason, log every access with the admin's ID,
and surface that log to the user on request. Building the restraint into the tool is the
only version of this that survives a growing team.

## 11. Testing

**Unit (Py)** — memory scoring; dedup thresholds; decay maths; segmentation key
derivation; all 8 koota calculations; transit scoring.

**Unit (Go)** — supersession state machine; summary trigger; notification quiet-hours
logic; daily fan-out concurrency bounds.

**Integration (Go, testcontainers)** — memory survives across conversations; paused
memory stops extraction; deleted memory never appears in a prompt again; summarisation
preserves open questions; daily generation produces exactly one row per user per day
with no duplicates (run the worker twice; assert idempotence).

**The memory isolation test.** User A has memories; user B asks a similar question;
assert **zero** of A's memory content appears in B's prompt or response. Run with
adversarial phrasing. This is the single highest-severity failure mode in the product —
a memory leak across users is a privacy incident, not a bug.

**Eval harness self-test** — graders tested against known-good and known-bad responses,
so a broken grader can't silently pass everything.

**E2E** — `mention a career goal → new conversation → AI references it → open memory
settings → delete it → new conversation → AI no longer references it`.

## 12. Security checklist

- [ ] **Memories strictly scoped per user; isolation adversarially tested**
- [ ] Special-category data not extracted unless volunteered as a durable fact
- [ ] Users can view, edit, delete and pause all memory
- [ ] Deleting a memory removes it from retrieval immediately (no cache lag)
- [ ] Memory content excluded from logs, analytics and error reports in both services
- [ ] Memory embeddings deleted with the memory
- [ ] Summaries inherit the conversation's access controls
- [ ] Daily predictions scoped per user; segment *templates* contain no PII
- [ ] Compatibility requires ownership of profile A; profile B owned or explicitly shared
- [ ] Compatibility never produces a "don't marry" verdict (eval-enforced)
- [ ] Notification payloads contain no personal content — title and deep link only
- [ ] Admin conversation access gated, reason-logged, surfaceable to the user
- [ ] All admin actions audit-logged
- [ ] Account deletion removes memories, summaries, predictions and compatibility reports

## 14. Risks

| Risk | Mitigation |
|---|---|
| **Memory leaks across users** | Adversarial isolation test in the eval harness, hard-gated in CI. Any failure is a P0. |
| Memory accumulates contradictions | Supersession + decay + user-visible editing |
| Users find memory creepy | Plain language, editable, pausable. Transparency converts the objection. |
| Daily generation cost explodes | Segmentation + Batch API. Verify the segment count in load testing, not production. |
| Daily worker runs twice and double-generates | `UNIQUE (user_id, date)` plus an idempotent task; asserted by running the worker twice in a test |
| Compatibility results cause real harm | Traditional framing enforced in prompt and eval; no verdicts; visible disclaimer |
| Eval harness becomes shelfware | Deterministic graders run on every push, free. If it only runs manually, it stops running. |
| LLM-as-judge unreliable | Judge only the soft quality rubric; every hard gate uses a deterministic grader |
